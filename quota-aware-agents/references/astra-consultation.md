# Bounded Astra consultation

Use this reference only for a concrete Astra second opinion. This is a workflow preference, not permission to switch the main model, a hard cost cap, or a replacement for host/tool approvals. Sol retains the user's goal, scope, implementation, integration, and evidence-based acceptance.

## When it is worthwhile

Propose consultation for an important unresolved reasoning/architecture/evidence interpretation question after reasonable initial analysis and with enough original material, or when an independent argument before a consequential architecture/data-protection decision has material value. The latter need not wait for repeated failures. Ordinary complexity, file count, one failed test, and routine review do not qualify.

First distinguish missing facts, permission/environment failures, tool limits, and actual reasoning difficulty. Fetch needed original evidence instead of substituting model opinions for observations. Provide one concrete question, inviolable constraints, necessary originals, established facts versus assumptions, the current Sol proposal/disagreement, and a way to test the answer. Avoid full-history dumps, leading summaries without originals, and broad requests to "check everything."

An automatically proposed worker must still have independent value and useful necessary parallel work for the main agent; do not invent paperwork or tests to fill waiting time. If the whole task hinges on the question with no useful parallel work, normally recommend that the user switch the main model rather than making Sol wait and relay. Do not switch it yourself. The user may explicitly request a bounded independent consultation even without parallel work; honor that scope when tools and permissions allow it.

## Bound the package

Normally use supported Astra/xhigh for one read-only consultation package and one returned conclusion, with at most one necessary brief clarification within the same question and investigation scope. Request options/recommendation, reasoning and counterexamples, assumptions/uncertainty, and minimum discriminating verification or an explicit inability to conclude. Do not give product/shared-record write ownership, installation/publication authority, or recursive delegation.

Sol advances necessary work that does not depend on the disputed decision; keep consequential disputed actions pending appropriate verification. Treat Astra's answer as an opinion to test against originals and minimal experiments, not authority, a vote, or proof. End when the decision and validation conditions are clear. Missing facts lead to bounded evidence collection; inconclusive answers remain explicit limitations. No standing Astra planning/approval/supervision chain.

A new core question, additional investigation, another Astra instance, or deeper discussion beyond the package needs a new value/scope check and, for an automatic proposal, a new notice. A package/returned conclusion can involve multiple model requests; this limit does not guarantee fixed usage or fees.

## Notify with a 30-second feedback window

This window applies to **automatically proposed Astra consultations**, not ordinary Sol/Luna packages, unless the user expands it. Prior explicit authorization must establish the default-execution rule. Silence, a preselected option, and an unclicked button are not approval. Without that authorization, or when a host/tool requires explicit approval, wait for the required affirmative authorization and continue unaffected work. A direct user request for this bounded consultation already authorizes it: briefly explain the arrangement and dispatch when ready, without asking the same permission or imposing a duplicate 30-second wait.

Explicitly adopting this policy establishes advance authorization within the user's stated scope until revoked or changed; do not request it again for each matching consultation. Merely discovering/loading/installing a public skill does not establish another user's consent. Across conversations use applicable user instructions or a trusted authorization record, not presumed shared chat memory.

For an automatic candidate, deliver an interactive notice using a currently available asynchronous question capability such as `request_user_input_async`, with suggested answers equivalent to "consult as planned", "skip Astra this time", and "explain or adjust", plus free text. Do not depend on the Plan-only synchronous question tool. A user instruction banning Astra or requiring explicit approval for this task prevails over default execution. If the question tool is unavailable or delivery fails, do not start an unanswered-notice timer or automatically consult; continue suitable direct work and state the concrete limitation.

Keep the visible notice compact, in the conversation language:

```text
Consultation <ID/revision>: <one concrete question>.
My current judgment and unresolved value: <why another analysis is worthwhile>.
Plan: supported Astra/xhigh, read-only, one conclusion and at most one brief clarification; <scope/originals>.
Speed follows the latest main selection; <relevant control/verification limit, if any>.
Meanwhile I will complete <different necessary work>.
Under your preauthorized rule, if no adjustment arrives within 30 seconds after this notice is delivered, I will run this plan. You can approve sooner, cancel, or ask for an explanation/change.
```

The ID/revision may be lightweight task-local context; no database, permanent workflow, or separate document is required. Do not invent a money estimate, and do not present scope/round limits as an enforced spending cap.

## Respond to feedback and changes

- Start the default **30-second** window only after successful interactive delivery; use real elapsed time. Continue useful independent work. Dispatch need not occur at the exact deadline: immediately before it, check latest messages, task activity, question necessity, permissions, and the still-valid notice/default rule.
- Explicit approval tied to the current plan may release it early. Explicit refusal cancels it; do not rename or re-notify the same request to bypass refusal. A task-scoped Astra prohibition continues through later phases until lifted; a one-time refusal is not a permanent ban.
- A question, request to explain, or scope adjustment **pauses default execution**. Answer/revise first; a materially revised notice starts a new window. A reply is neither automatically consent nor rejection, and a question is not silence.
- On no response, execute only after the window has elapsed and all validity/authorization conditions still hold. Record the actual basis as "executed under the preauthorized default", never "approved by the user."
- Before dispatch, a late response governs the plan. After dispatch, cancellation stops subsequent consultation and interrupts the worker promptly where supported, preserving valid results and actual call evidence. Do not promise reversal of consumed requests/usage or continue consequential actions under a rejected plan.
- Bind each notice to the current task, concrete question, and plan revision. Material changes to scope, goal, Astra model/effort, instance count, investigation authority, or explicit budget invalidate it and require a new notice. An old approval cannot approve a new revision; clarify an ambiguous late response rather than transplanting it to another package. Changed main model or user goals require reassessing whether consultation is still needed; cancel obsolete questions.
- Speed uses the separate [speed-following](speed-following.md) settings epoch. A notice that already says "follow the latest main speed" does not need reopening for every ordinary toggle. If a change breaches an explicit speed/budget constraint, revise the plan. Unknown/unsupported controls remain unknown/unsupported; a message cannot apply speed.
- Handle the window only within the active task. Do not create a background timer, automation, new chat, or later autonomous dispatch. A finished, replaced, or interrupted task cannot release an expired notice by itself; on resumption reassess need/authorization and re-notify as appropriate. Never bypass system/tool approval requirements.

Use a lightweight state only as needed: candidate → notified/waiting → explicit approval or preauthorized default release → running → accepted/stopped, with clarification/cancelled/expired alternatives. Accept once with appropriate original evidence, retaining existing user decisions; when analyses disagree, seek a falsifiable distinction instead of repeated opinion exchange.
