# Following the main chat's speed

Use this reference when speed synchronization matters or the host exposes controls or verified speed-specific inheritance. Follow the user's latest main-chat speed unless they specified a worker override. Model, reasoning effort and speed are separate. A tier label such as `priority` identifies a UI speed only if the host documents that mapping.

Read the current desired mode at dispatch or continuation and after an observed change. A user instruction establishes the desired mode. Applied speed requires a documented control result or fresh worker runtime evidence. Use the host's speed-specific inheritance or setter and respect supported combinations. If the setting is unsupported or unknown, state a consequential limitation once and continue suitable authorized work. Use a permitted fallback when an explicit requirement rules out the proposed route.

For hosts with live updates, track the latest settings revision for each affected worker. Serialize updates, coalesce obsolete ones and ignore stale confirmations, even when the mode cycles back to the same value. After an in-flight change, recheck the current target before claiming synchronization. A new spawn confirms only its own configuration. A worker message can convey changed instructions; speed application needs runtime evidence.

Reuse completed work. Update active workers at the next supported boundary and idle workers on reuse. Replace a worker only if the configuration requires it, the tool supports it and ownership can transfer safely. Follow the host's documented effective time for in-flight requests. Keep verification in the active task, using the controls the host exposes.
